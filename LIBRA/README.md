# LIBRA — Smart Library Seat Finder

**Code Fuzion 2026 · Lovely Professional University · Problem M4**

A real Firebase-powered, responsive HTML/CSS/Vanilla JavaScript seat-booking app for a sample library with three floors and 20 seats on each floor. It ships as **source code**. You must connect a Firebase project before authentication and live booking can run; the included landing page preview is labeled sample UI rather than live data.

## What works when configured and deployed

- Email/password Firebase login and sign-up, profile name, logout.
- Live multi-floor map with available / reserved / occupied / break / unavailable states.
- 10-minute reservation hold followed by QR check-in at the chosen seat.
- **Atomic one-seat-per-student booking** using a trusted server-side Firestore transaction against both the seat document and `activeBookings/{uid}`. Concurrent claims of one seat: only one can succeed.
- Seat QR codes with 32-byte cryptographically random tokens (generated by the admin seed script). Only admin users can retrieve the QR payload. The server compares SHA-256 token hashes, checks the caller's active booking, seat ID and current reservation state.
- 20-minute break countdown stored as absolute timestamps, restored after page refresh. Return requires another scan of the real seat's QR code.
- Automatic release via **Cloud Tasks** at a reserved/break deadline, plus a once-per-minute **Cloud Scheduler** recovery job if a task is delayed or enqueue fails. Release operations are idempotent and verify the same booking still owns that seat.
- Admin dashboard gated by Firebase custom `admin` claims, with actual recent booking history, check-ins per hour, floor usage, most-used seats, long-session flags, and admin-only printable QR sheet.
- Safe offline behavior: the user sees a cached/offline warning and booking changes are disabled. Changes are never recorded as successful in offline demo mode.

**Important timing truth:** Firestore normally pushes changes promptly to all connected devices, but **no guaranteed 5-second SLA** is provided by this design. Cloud Tasks can dispatch later than the scheduled time, and the fallback cleanup runs every minute. The browser countdown reaches 00:00 immediately and the *server* remains authoritative. Verify the actual end-to-end refresh latency in the hackathon venue and state the limitation if judges ask.

**QR security limitation:** A static printed QR proves the user possesses its secret, not that a person is physically standing next to the seat; somebody who photographs/shares the QR can reuse it. A real production deployment should add rotating physical tokens, NFC/proximity checks and App Check/rate limiting. The fallback manual QR input is explicitly labeled **DEMO FALLBACK** and still verifies the token on the server.

## Quick start for Windows 10/11 (VS Code + PowerShell)

### 1. Create your own Firebase project

1. Visit [Firebase Console](https://console.firebase.google.com/) and create a new project, e.g. `libra-hackathon-2026`.
2. In **Build → Authentication → Sign-in method**, enable **Email/Password**.
3. In **Build → Firestore Database**, create the default database (use **production mode**, not open/test mode). Select a nearby region; note that Cloud Functions are configured for `asia-south1` in this project, independently of Firestore's location.
4. Register a **Web App** via Project Settings → Your apps → Web. Copy its public web configuration values into `js/firebase-config.js`. Replace `apiKey`, `authDomain`, `projectId`, and `appId`. The public web API key is designed for browser use; it is **not** a service account key.
5. To deploy Cloud Functions and timed Cloud Tasks, Firebase requires the **Blaze (pay-as-you-go) billing plan**, even if usage is tiny. Review [Firebase pricing](https://firebase.google.com/pricing) and set Google Cloud billing **budget alerts**. Cloud Scheduler and Cloud Tasks may incur charges. If you cannot enable Blaze, the complete automated, cloud-backed implementation cannot be deployed on Spark; use the Emulator Suite for development and do not claim the hosted app meets every requirement.
6. Turn on Cloud Tasks and Cloud Scheduler APIs if Firebase / Google Cloud asks you when deploying. You may need appropriate IAM permissions to enqueue Cloud Tasks.

### 2. Install tools

Install Node.js 22 LTS (needed **only for deployment and trusted Firebase backend**, not the browser UI), VS Code, Git (optional). In PowerShell:

```powershell
npm install -g firebase-tools
firebase login
cd C:\path\to\LIBRA
firebase use --add
cd functions
npm install
npm test
cd ..
```

`firebase use --add` should select the Firebase project you just created. The `.firebaserc` file is excluded from Git. Use `firebase projects:list` to verify your account can see the project.

### 3. Deploy server logic and rules first

```powershell
firebase deploy --only firestore,functions
```

If the deploy reports Cloud Tasks permissions issues, check Firebase's [official Task Queue documentation](https://firebase.google.com/docs/functions/task-functions#troubleshooting). No service account JSON should ever go into a web file or GitHub repository. On a first deployment, the scheduled cleanup and task queue may take time to initialize.

### 4. Seed 60 seats and QR secrets using **Admin SDK credentials**

This is a one-time local setup action. To avoid placing a private key in source code, preferably use the **Google Cloud CLI Application Default Credentials** (`gcloud auth application-default login`) for an account with suitable Firebase/Firestore permissions. Alternatively, generate a Firebase Admin SDK service-account private key in Firebase Console → Project Settings → Service accounts. **Keep that file outside `LIBRA`, private, and never share/upload/commit it.**

In PowerShell, if you chose a private key file:

```powershell
$env:GOOGLE_APPLICATION_CREDENTIALS="C:\secure-folder\my-firebase-service-account.json"
cd C:\path\to\LIBRA\functions
npm run seed
```

Or, if Google Cloud CLI ADC is already configured, simply run `npm run seed`. Seeding again **does not reset existing seat bookings or regenerate old QR tokens**. It makes 60 real seat records: F1-S01 to F3-S20, including two unavailable/maintenance samples.

### 5. Create your administrator

Open the app (see step 6) and sign up with the email that you want to act as the administrator. Then in the same PowerShell window that has valid Admin SDK credentials:

```powershell
cd C:\path\to\LIBRA\functions
npm run admin -- your-admin-email@example.com
```

**Sign out and log in again** to refresh the Firebase ID token. Only people with the server-set `admin: true` custom claim can read admin-only data. A student editing browser JavaScript or profile fields cannot grant themselves admin access.

### 6. Run locally or deploy

To run the static website on your laptop from the `LIBRA` root, use Python if installed:

```powershell
python -m http.server 5500
```

Open `http://localhost:5500`. Alternatively use **VS Code Live Server**. **Do not open `index.html` as `file://`**, because ES modules and Firebase need a web origin. Authorize `localhost` in Firebase Authentication → Settings → Authorized domains if Firebase asks you. Camera QR scanning typically requires HTTPS, but localhost is accepted as a secure context by modern browsers.

To publish the web pages securely:

```powershell
firebase deploy --only hosting
```

Use the Firebase Hosting URL printed by the command (`https://YOUR_PROJECT_ID.web.app`). Enable the correct Hosting domain in Firebase Authentication authorized domains if required.

### 7. Print QR codes and demonstrate check-in

1. Log in as an admin and open `admin.html`.
2. Scroll to **Seat QR print sheets**, choose **Print QR sheets**, then place each paper at its corresponding physical seat.
3. Open a different browser/profile or Incognito window as a student. **Register and reserve** a green seat.
4. **Scan the matching seat's QR** with the student device to check in. The red occupied tile should appear on all online devices.
5. Start Break. The seat turns orange and its countdown continues over refresh. Scan the *same* QR before 20 minutes to resume occupancy.
6. If the camera cannot be accessed, the student can expand the clearly labeled **DEMO FALLBACK**. An administrator can use **Copy QR text (demo)** from the admin QR panel and provide the matching payload for the student to paste. This is **still verified against the actual Firebase booking and secret**; it is not a fake check-in.

## Database schema

| Collection / document | Main fields | Who can read |
| --- | --- | --- |
| `users/{uid}` | `displayName`, `email`, `createdAt` | Owner + admin |
| `seats/{seatId}` | `floor`, `seatNumber`, `label`, `zone`, `status`, `activeBookingId`, `reservedUntilMs`, `breakExpiresAtMs`, timestamps | Signed-in users |
| `seatSecrets/{seatId}` | `token`, `tokenHash`, `createdAt` | Admin only (Admin SDK bypasses rules on server) |
| `activeBookings/{uid}` | `bookingId`, `seatId`, `floor`, `status`, deadline fields | Owner + admin |
| `bookings/{bookingId}` | `uid`, `email`, seat/floor, check-in time, break count, occupied duration, status, ended reason | Owner + admin |
| `breakSessions/{bookingId-bN}` | `uid`, booking and seat IDs, break start/end, status | Owner + admin |
| `adminAnalytics/{id}` | Reserved for future precomputed aggregates | Admin only; no fake seeded data |

All status and booking writes are handled **only** by Cloud Functions using the Admin SDK. Firestore Security Rules deny direct client writes to seats, bookings, breaks and secrets.

### State transitions

```
AVAILABLE ── bookSeat ──> RESERVED (10-minute check-in deadline)
RESERVED ── matching seat QR ──> OCCUPIED
RESERVED ── cancel / deadline ──> AVAILABLE
OCCUPIED ── startBreak ──> BREAK (20-minute deadline)
BREAK ── matching seat QR before deadline ──> OCCUPIED
BREAK ── cancel / deadline ──> AVAILABLE
OCCUPIED ── end session ──> AVAILABLE
AVAILABLE ⇄ UNAVAILABLE (admin maintenance callable only)
```

### Admin metrics: what they mean

- Peak hours = count of **actual QR check-in events** grouped by the hour shown in the admin viewer's local timezone.
- Most-used seats = count of actual check-ins per seat.
- Potential hogging = any individual session with **at least 2 hours of cumulative occupied time** (break time excluded). This flags long use; it does not prove bad intent.
- Admin displays up to the **500 most recent bookings** in the charts and 100 newest rows in the table. Statistics are therefore a *recent-history sample*, not lifetime totals, if more than 500 bookings exist.
- All metrics are generated from actual records; the landing-page example is specifically labeled illustrative, not live.

## Known limitations and production improvements

- There is no guaranteed 5-second latency/SLA. Under normal network conditions Firestore listeners generally update quickly; test network, queue delays, cold starts and recovery on real devices.
- In a camera/browser outage, manual QR input is a labeled demo fallback (no fake result). QR contents should be treated like a physical access credential.
- Cloud Tasks and the minute backup run in the cloud and require Blaze. They are not simply browser timers.
- Emulator Suite is useful without billing for local testing, but scheduled task timing and actual cloud costs need separate cloud testing.
- While offline, existing cached seat displays might be stale. Server transactions reject conflicting bookings when connectivity returns.
- No push notifications are sent while the page is closed. On return, booking state and expiry notice are shown through Firestore; Web Push would be a future enhancement.
- Using a static QR token provides possession-based proof, not strong physical presence. Add rotating check-in tokens or NFC/IoT validation for production.
- Deployment requires configuration by the student team's own Firebase account. No live deployment or production concurrency test has been performed as part of this source-code package.
